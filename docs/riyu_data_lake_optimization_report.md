## 1,000対局の加工比較

Mac M4の1台で方式を順番に実行。SQLite順の同じ先頭1,000件、4ワーカー、16対局/シャード、方式D、チェックポイント32、Row Group 8,192行、ZSTD 3。Arrow IPCは非圧縮の中間形式を測定した。壁時計はソースのSHA-256計算を含み、テーブル比較の時間は除く。CPUは子プロセスのuser＋system、RSSは各経路のピーク。ParquetはRustとPyArrowのライター実装差で物理バイト列が異なる。

| 経路 | 壁時計（Rust＋後段） | CPU | ピークRSS | 中間 | Parquet |
|---|---:|---:|---:|---:|---:|
| A: Rust Arrow → Parquet | 93.45秒 | 160.29秒 | 2.68 GB | 0 | 276.59 MB |
| B: Rust Arrow IPC → PyArrow | 94.91＋8.42秒 | 168.53秒 | 2.50 GB | 4.13 GB | 279.19 MB |
| C: Rust JSONL → PyArrow | 89.74＋195.18秒 | 354.64秒 | 2.44 GB | 7.09 GB | 279.19 MB |
| 参考: 前回 | 168.9＋253.9秒 | 別測定 | 2.53 GB | 7.09 GB | 242.32 MB |

アクション軸の照合列などを今回の3経路で共通に有効化したため、前回の最終ファイル容量との比較には列差が含まれる。同じ列で比較するとAはCより壁時計で約67%短く、約10.7入力対局/秒、4,842意思決定/秒。OSのI/Oブロックカウンタは全測定で0を返し、物理デバイスI/Oは未計測。論理的には全方式が2.21 GBの元DBを初回ハッシュ読込する。B/Cは上表の中間ファイル全体を書き、継続工程で再読込する。

Arrowの行と属性は共有スキーマで変換し、意味的ActionId、タイブレーク後の順位、選択不能な応答のnull、候補のソート順を保持した。Rust直書きは各シャードを別の作業ディレクトリで組み立て、表の件数、サイズとSHA-256を記録した後にディレクトリを公開する。再開時に同じ構成でコミット済みシャードを検査する。JSONL経路は小範囲ごとに統合可能。明示オプションを選んだ場合だけ、入力チェックサム、Parquetの読戻し件数、出力の公開を確認して中間シャードを削除できる。今回の測定では比較と診断用に中間ファイルを保持した。

## Rustの計測と設定

直接出力1,000対局のワーカー内累計。合法手11.05秒、攻撃・受け入れ25.23秒、観測生成・状態ハッシュ等13.93秒、再現（履歴ハッシュ等を含む）5.88秒、Beliefの手牌・待ち0.86秒、守備（即時ロンと点数）1.82秒、XML正規化0.78秒。前回は合法手65.29秒、攻撃63.90秒、観測33.55秒、再現19.03秒だった。計測条件とワーカー数が異なるため単独の最適化効果とは解釈しない。

同種牌の手出し・ツモ切り等で繰り返すシャンテン計算を候補内で共有し、リーチ候補判定でも攻撃教師と同じ厳密キャッシュを利用する。イベント更新は履歴ベクタの毎回コピーを省き、失敗時の状態復元は維持した。フル手牌のキャッシュキーは34牌種の枚数と副露数。スート内部は3ビット枚数をキーとする部分形の動的計画法。ワーカー間共有を導入しておらず、ロック競合・メモリ予算との比較は未測定。1,000対局では手牌キャッシュ1,838万ヒット、1億2,580万計算、ヒット率12.8%。スート内部のキャッシュヒット率はこの数字に含まれない。

## 可視情報と保存構造

同じ30四麻対局の122,700観測イベントを、公開30,675行と自席私有15,408行に分解した。ZSTD 3で0.549 MBから合計0.266 MBへ約52%減り、全観測イベントをバイトレベルで再合成できた。単発のファイル読込は9.2 msから2.7 msだが、Pythonで全席を再合成する追加処理は0.48秒。研究用の重複排除には有効で、直接的な学習経路への採用は結合をRustに寄せた後に再評価する。

18,469スナップショットを型付きの手牌、河、副露、場況列に置換した試験は、1.607 MBから1.012 MBに約37%減り全項目が一致した。今回のPythonによる型付けは2.11秒、書込は52 msから136 ms、読込は47 msから38 ms。現時点の正本では元のJSONバイナリ列を維持し、型付き版を導入する際はRustで直接構築する。

Belief Fullは34バイト＋赤マスク＋ツモ意味コードのまま維持。合成テストで他家の非公開手牌を交換しても行動者の観測・履歴・合法手ハッシュが一致した。通常牌のコピー交換は意味的入力に影響しない。ローダーは意思決定IDと半荘分割を照合し、`ModelInput` と `PolicyTarget` に分離する。特徴量は本人手牌・本人ツモ・公開ドラ・現時点点数と残り牌数を読む。異なる観測履歴は時系列キャッシュを分離する。実運用での別アカウント・別マウントによる制限は未検証。

## 特殊ルール・守備・Belief品質

全328,424対局を読み取り専用で走査し、珍しい局を含む52対局をローカルで選定。全52対局を再現し、三家和6局、四槓散了6局、責任払い6和了、搶槓6和了、複数ロン7局、リーチ宣言牌のロン16件、西入18局を確認。責任払いを含む452件の和了収支を独立の支払計算で照合し、同点7件は元精算順位と一致した。三家和から個々の確定しない応答を学習に追加していない。

上記52対局と先頭96対局の別標本（四麻66、三麻30）で、実際の打牌ロン合法593件、単独ロンの確定失点381件、複数ロンの和了者24件、裏ドラ付きの実結果195件を確認。条件付き失点には一時・リーチ後の振聴不明、裏ドラと責任払いのステータスを保持する。複数ロンの個別値を実損失として合算しない。Belief Fullの5,823手を別の投影イベント再生で復元し、枚数、赤牌、本人ツモと比較した。待ち881件とシャンテンをPythonの独立実装と照合した。合成テストでは通常・リーチ後の振聴、嶺上ツモと海底の排他、未公開の槓ドラ、非公開の手牌や物理牌コピーを入れ替えたときの観測不変性を確認。Rustテスト47件、Pythonテスト8件が通過し、Clippyと整形チェックも通過した。

時期を分散した1万対局の最初の試行は784対局の時点で停止した。782対局を再現、2対局で再現不一致を記録した。原因は、最終嶺上ツモに海底役を重ねた点数と、通常の順番でチーした後の一時フリテン解除だった。修正後の再試行は1,440対局の時点まで進み、1,439対局を再現。途中で別のポン後の一時フリテン判定が見つかって自動停止した。

離れた席からのポン後は、判定が変わり得る場合に一時フリテンを「不明」とする。実牌譜のロンは記録し、合法手集合を確定できない行は方策訓練から除く。3件の元牌譜はいずれも最終修正後の回帰試験で再現し、最後の1件では16表の出力が全経路で一致した。

振聴の修正後に停止地点までの1,440対局を方式Cで再加工。再現拒否0件で15,190局・933,857意思決定を生成した。壁時計199.35秒、ピークRSS 2.57 GB、Parquet 471.90 MB。シャード内の読込・処理・書込の合計は冒頭320対局27.95秒、末尾320対局33.39秒だった。局数や候補数が異なるため、この差から熱による低下は判定できない。固定分割は訓練1,174、検証144、最終評価122で、重複割当0件。

1,440対局の独立監査では、和了の支払い12,785件と、別手順で再現したBelief Full 14,358手・待ち2,122件を検査した。ここでは再現拒否がなくても、単独ロンの条件付き失点に3件の不一致があった。3件すべてが槓ドラの後めくりがあるケースで、公開済みドラだけの打点が確定値とされていた。守備教師の修正では、未公開の槓ドラがあるときに `loss_status=pending_kan_dora` として確定失点をnullにする。公開済みドラに基づく打点とロン合法性はそれぞれの列に残す。問題の3対局を再加工し、3件ともこの状態に分離され、同じ独立監査に合格した。1,440対局全体の数値は槓ドラ修正前の実測である。

1万対局は完走していない。停止の原因になった再現不一致を修正した後、得点教師の問題が1,440対局の独立監査で判明した。局面再現の成功とは別に、最終修正後の守備教師を広い標本で再検証する必要がある。

四麻半荘218,858対局へ単純外挿すると、暫定でMac約8時間、方式C約72 GB、方式D約84 GB。Cは最終版の1,440対局を基準に約8.4時間、Dは混在1,000対局を基準に約7.9時間。測定条件が異なるためC/Dの速度差の比較には使えない。時期分散1万対局のCは同じ比率で約23分、約3.28 GB。本番では空き容量、拒否の調査用領域、ファイルサイズを別途確認する。

TSUBAMEでは同一コードを範囲分割できる。Linuxでの同一論理出力、転送帯域、scratch容量、元牌譜の外部利用許諾を確認してから判断する。例えば実効100 MB/sなら2.21 GBの元DBの転送だけで約22秒、本番規模の約72 GBの出力で約12分が理論上必要。実際の転送・キュー待ち・利用時間は未測定。Macの直接加工が容量面も含めて成立するなら、TSUBAMEは学習・自己対戦側を優先する。データ転送やジョブ投入は行っていない。[TSUBAME4.0ジョブスケジューラ](https://www.t4.cii.isct.ac.jp/docs/handbook.ja/jobs/)

## 再現コマンド

プライベートな出力先を使用する。以前と同じ順序で比較する場合の例。

```sh
cargo build --locked --release -p riyu-data-lake
python tools/compare_riyu_arrow.py ARCHIVE.db PRIVATE_COMPARISON \
  --authorization-reference APPROVED_REFERENCE --limit 1000 --workers 4
python tools/riyu_lake_inventory.py ARCHIVE.db PRIVATE_PLAN --size 10000
target/release/riyu-data-lake ARCHIVE.db PRIVATE_OUTPUT \
  --authorization-reference APPROVED_REFERENCE --plan PRIVATE_PLAN/balanced.plan \
  --profile C --limit 10000 --workers 4 --stop-on-replay-error
python tools/validate_riyu_lake.py PRIVATE_OUTPUT --max-shards 6
```

推奨順は特殊例・守備の回帰照合、時期分散試行の合格判定、型付き観測とロード経路の見直し、Linuxでの同一論理出力確認、その後の本番加工。試験結果を確定するまで、全量加工やモデル学習を開始しない。
