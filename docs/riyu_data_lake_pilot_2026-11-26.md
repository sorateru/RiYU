# RiYU Data Lake v1 試験実装・検証報告

2026-11-26 / macOS、Apple M4、メモリ24 GB

元資料は[監査報告](riyu_data_foundation_audit_2026-11-25.md)と[更新した詳細設計](riyu_data_schema_design_2026-11-26.md)。以下の数値は試験加工の実測。全量の値は観測範囲からの外挿である。

## 結果と採用する構成

SQLiteの先頭1,000対局を読み取り専用で処理した。四麻722対局を再現し、三麻278対局は完全イベントの正規化まで進めた。正規化・再現エラーは0件。四麻7,345局から452,444意思決定を生成した。四麻は東南戦647対局（GO 169）と東風戦75対局（GO 225）、三麻はGO 185だった。先頭の連続標本なので、年全体の卓・時期構成を代表する保証はない。

長期正本は元SQLiteと型付き完全イベント。研究用の観測復元は観測者別イベントと32イベント間隔のチェックポイント（C）。学習のランダムバッチには必要な観測だけを軽量スナップショットにする方式（D）を選べる。Belief Fullは固定長34バイトの牌種別枚数に、暗手の赤マスクとツモ牌の意味コードを併設する。Parquet初期設定はZSTD 3、8,192行ごとのrow groupとする。試験ファイルは16対局単位。運用ファイルの目標サイズは未決定。

## 実装範囲とデータ契約

| 層 | `riyu-data-lake-pilot/1` のデータと処理 |
|---|---|
| L0 | SQLiteをreadonly接続。コンテナSHA-256、展開後payload SHA-256、元レコード位置、記録時刻文字列、利用許諾参照を保持。生時刻のタイムゾーンは未設定 |
| L1 | Rustでbzip2・XMLを処理。GO/UN/TAIKYOKU/INIT/SHUFFLE/BYE、全ツモ・打牌・鳴き・槓・ドラ・リーチの2段階・終局を型付き化。属性を残し、未知属性は制限領域の拡張列から参照可能 |
| L2 | 物理牌台帳で牌の所属を検証。Rustの各席視点で手牌・河・副露・巡目・点数・局進行・ドラ・一発・振聴を追跡。観測者への安全なイベント投影と復元点を保存 |
| L3 | 意思決定ごとの意味的候補を定義順で格納。ActionIdは正規化バイト列のSHA-256先頭64ビット。実行に用いる物理牌コピーは制限表に分離 |
| L4 | 方策、攻撃、守備、Belief Lite/Full、局・和了・半荘結果を別表に保存。実結果は局・対局・選択行動を介して参照 |
| L5 | 半荘IDの固定ハッシュで80/10/10に割当。同じpayload IDの重複入力、重複範囲、欠損範囲、チェックサム違反を検出。非対応ルールとエラーはステータスを記録 |
| L6 | 状態・履歴・意味的候補のハッシュ、Encoder版と設定からキャッシュキーを作るAPI。モデル固有特徴量を生成する処理は別工程 |

Rustは対局単位の並列化と1回の再現での教師生成を担当する。Pythonは1シャードずつ検証済みの対局をArrowに組み立て、Parquetへ書く。受け渡しは対局単位のJSONLスプール。同じシャード名への部分上書きを防ぎ、完成したシャードは入力・実行バイナリ・設定・件数・SHA-256を検査して再利用する。Parquet統合は新規出力先に検証済みreleaseを公開する方式。途中失敗時はRustシャードから統合を再実行する。

入力は `inputs/`、教師は `targets/`、元情報と物理牌は `restricted/`。通常の入力ローダーは入力テーブルのみ列挙し、リンクで入力ディレクトリの外へ出る参照を拒否する。各席の投影は他席ツモをnullにし、本人牌の意味コードからも物理コピー番号を外す。`restore_observation` は入力テーブルだけで本人の局面を復元し、状態ハッシュを照合する。研究ジョブは観測者で絞り、学習ジョブには確定した意思決定バッチを受け渡す。別ユーザーやマウントによる隔離は実運用側の追加検証項目。

守備教師の `ron_legal` は実隠れ手牌が与えられた同時点の判定。過去の応答の打ち切りによって振聴が不明で、合法性が変わり得るセルはnull。裏ドラや責任払いが条件となるときは、裏ドラ・責任払いなしの仮定値と正確な条件付き失点を分ける。三家和・複数ロン・積み棒を含む集約失点は、このセルの単純和では求めない。和了確率は別の教師仕様である。

応答窓の選択を確定できるときだけ方策に採用する。通常の次ツモで閉じた窓は確定PASS候補。優先行動によって打ち切られた窓では選択欄をnullにする。合法手が振聴によって不確定なら、選択根拠と合法集合の状態を別に記録し、方策の訓練マスクを落とす。採用数は実選択376,574、確定PASS 73,644。打ち切り2,225件と合法集合不明の確定PASS候補1件は訓練対象外。

### 加工例（合成例）

`<D104/>` のようなタグを、直前のツモと照合してseat 0の9索の手出しとして扱う例。直前に別コピーの9索をツモっていれば、同種のツモ切りも別の意味候補になる。この例の牌順・候補番号は説明用。

| 消費先 | 保存例 |
|---|---|
| 制限イベント | `{type: discard, seat: 0, tile: {id: 104, kind: 26, red: false}}` |
| 観測イベント | `{type: discard, player: 0, tile: {kind: s9, red: false}, tsumogiri: false}` |
| 合法候補 | 手出し `[1, 0, 52, 0]`、ツモ切り `[1, 0, 52, 1]`。物理実行情報は別表 |
| 方策教師 | `choice: 4`、`choice_status: selected`、`legal_status: complete`、`trainable: true` |
| 終局教師 | 局キーで四席の点数・局収支・和了結果へjoin。未選択候補の結果として書かない |

### Belief Fullの手牌表現

32対局のうち先頭16対局から、同じ31,425他家手牌を抽出。ZSTD 3。ファイルサイズには比較用のストリームキー、ツモ牌・赤マスクも含む。復号は34枚数へ変換する時間。学習配列への変換は後段の連続NumPy float32への変換で、PyTorch訓練やGPU転送とは別。

| 方式 | 圧縮前の手牌本体（KB） | Parquet（KB） | 書込 / 読込（ms） | 枚数への復号（ms） | float32化（ms） |
|---|---:|---:|---:|---:|---:|
| uint8 × 34 | 1,068.5 | 93.0 | 6.0 / 1.4 | 0.11 | 0.66 |
| 3ビット × 34 | 408.5 | 87.3 | 6.2 / 1.4 | 3.78 | 0.88 |
| 意味牌コード列 | 385.2 | 90.4 | 7.5 / 1.5 | 179 | 0.84 |
| 物理牌ID列 | 385.2 | 96.8 | 6.1 / 1.4 | 80 | 1.03 |
| 意味牌コード差分 | 50.2 | 48.2 | 4.9 / 1.5 | 152 | 0.74 |
| イベントから復元 | 追加列なし | 追加なし | 上の復元表を参照 | 物理台帳を別途再生 | 未計測 |

34枚数のファイルは3ビットより6.6%大きく、このPython実装では復号が約35倍速い。頻繁なランダムバッチは34枚数、アクセス頻度の低い保管は3ビットと差分が候補。物理コピーの正本はL1に一度保存する。34枚数でZSTD 1/3/6を比較したファイルサイズは94.3/93.0/86.5 KB、書き込みは6.8/6.0/8.5 ms。6の追加圧縮は確認できたが、広い標本での比較は次回。

## 品質の合格状況

- 722対局の全イベントで物理牌の所属保存則と対象席の手牌を照合した。和了は6,208件の符・手の点数が元XMLと一致し、6,166和了局で各席の点数移動を元の支払情報と独立照合。42局のダブロン、チー6,181件、ポン8,325件、大明槓43件、加槓230件、暗槓366件を通過した。
- 九種九牌87局、四風連打5局、四家立直2局、流し満貫1局。三家和・四槓散了・責任払いを含む実例は標本内で未検証。
- Rustテスト43件。合成牌譜の非赤コピー置換で、観測状態・履歴・候補ハッシュは同一、物理実行情報のみ変化。Pythonテストでは同一状態に異なる履歴を与えるケース、入力から制限パスへの参照を検査。
- 和了なし・未実施・不明を一律0にしない。観測不能な応答での選択値、重複候補、候補範囲外の選択はParquet変換時に検査する。
- 1,000対局の完成スプールを別ワーカー数で再実行し、63シャードのハッシュ・件数を検証して再利用した。

## 実行単位とファイル

ローカルの許諾参照を確認した上で次のコマンドを使用する。出力先はアクセス権が本人に限定された作業領域。比較した全スプールや牌譜データはGitに置かない。

```sh
cargo build --release -p riyu-data-lake --locked
target/release/riyu-data-lake ARCHIVE.db PRIVATE_SPOOL \
  --authorization-reference REFERENCE --limit 1000 --workers 6 --measure-restore
python tools/pack_riyu_lake.py PRIVATE_RELEASE PRIVATE_SPOOL --profile D --checkpoint-interval 32
python tools/bench_riyu_lake.py PRIVATE_SPOOL --hand-matches 16 --release PRIVATE_RELEASE
```

| ファイル | 変更 |
|---|---|
| `Cargo.toml`、`Cargo.lock`、`engine/data-lake/Cargo.toml` | Rust加工クレートと依存関係 |
| `engine/data-lake/src/source.rs`、`physical.rs`、`replay.rs` | 入力、正規化、台帳、時系列再生、四視点投影、復元検証 |
| `engine/data-lake/src/actions.rs`、`teachers.rs`、`shanten.rs` | ActionId、天鳳の合法手制約、教師、同一スート形の計算再利用 |
| `engine/data-lake/src/main.rs` | 読取専用SQLite、上限付きレンジCLI、シャード検証と再開 |
| `engine/core/src/legal.rs`、`state.rs`、`lib.rs` | 元牌譜の裏ドラによる点数照合、嶺上の文脈、加槓の搶槓窓での一発処理 |
| `tools/pack_riyu_lake.py`、`tools/bench_riyu_lake.py` | 型付きArrow/Parquet分割、独立点数検証、保存・加工測定 |
| `python/mahjong_ai/data/lake_view.py`、`tests/python/test_lake_view.py` | 可視入力・復元、特徴量ハッシュ、情報境界のテスト |
| `tools/riyu_lake_array_worker.sh` | 事前分割した範囲を処理するTSUBAME向けの薄いアダプター |

TSUBAME4.0はAltair Grid Engineを使う。範囲表の行を `SGE_TASK_ID` で選び、同じCLIで各シャードを作り、別工程で統合する。開発と次の標本比較はMacで行える。TSUBAMEは大量のCPU時間を使う処理や今後の学習で候補になり、外部保管・処理を含む許諾と、Linuxでのゴールデン出力・I/Oを確認してから採用する。[TSUBAME4.0公式利用の手引き](https://www.t4.cii.isct.ac.jp/docs/handbook.ja/jobs/#5218)

## 次の検証

1. 天鳳の三家和・四槓散了・責任払い・終盤の特殊な点数をカバーするfixtureを追加する。GO 169/225以外と三麻は正規化対象。壁・王牌の完全復元はSHUFFLEのアルゴリズムを別途検証する。[天鳳公式の四麻ルール](https://tenhou.net/man/index.html)
2. 監査用の完全イベント、教師、他席観測を本番の学習プロセスから確実に隔離する。公開の重複投影とJSONバイナリ列を減らし、Rust直書きArrow/ParquetまたはArrow IPCのバッチ転送に切り替える。分割は元IDだけでなく意味的重複、期間・対局者跨ぎも検証する。
3. 固定の標本セットを使い、事前に定めた1/2/4/6ワーカー、複数のrow group/ファイルサイズ、メモリとディスク温度による速度低下を単独実行で測る。A/CのParquetからのランダムバッチ、Belief FullのPyTorch転送まで計測する。
4. 1,000対局の結果に加え、特殊ルール・外部権限・再現性の問題が解決した時点で、時期を層化した10,000対局を検討する。段位戦報酬には時期・サービスごとの検証済みRewardSpecが必要。探索教師は別の実験段階で取り扱う。
